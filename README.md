# 智能账本 (Smart Ledger)

> **当前版本：`v1.0.0`（开发中，准备正式发布）**

一款基于微信云开发的个人财务管理小程序，支持微信支付账单导入、多维度统计分析等功能。

## 版本号约定

采用语义化版本 `MAJOR.MINOR.PATCH`，**首次对外发布前一律停留在 `0.x`**：

| 号段 | 递增条件 |
|------|----------|
| `MAJOR` | 不兼容的变更——例如账单数据结构、云函数入参调整，会要求用户清库重导 |
| `MINOR` | 向下兼容的新功能（如新增一个页面或一类统计维度） |
| `PATCH` | 向下兼容的问题修复（如某个数字算错、某个样式错位） |

云函数目录下的 `package.json` 版本号跟随主版本同步调整，便于排查「线上跑的到底是哪一版」。

### v0.8.0（已完成 · 未发布）

这一轮让「AI 分析」页**真的开始出结论** —— 但接的不是大模型，是**规则引擎**。

- ✅ **七条检测规则**，不满足条件就不输出（而不是凑满几条）：
  预算进度 / 支出涨跌 / 消费结构集中度 / 小额高频 / 常去的地方 / 周末效应 / 记账连续性
- ✅ **每条结论都带「依据」（evidence）**：合计、占比、笔数、天数逐项摊开，
  用户可以自己对着账单核 —— 这是本项目的老规矩，派生数字不给依据就等于只能相信
- ✅ **规则引擎放在 `cloudfunctions/getStatistics/lib/insight.js`（纯函数）**：
  查库与摘要组装在 `index.js`，规则本身不碰数据库，所以能被离线单测逐条验证。
  ⚠️ **不新建 aiAnalyze 云函数**：微信云函数不能 require 云函数目录外的文件，
  新建就得复制一遍 `periodRange` / `fetchAll` / `composeBudget`，两处口径迟早漂移
- ✅ **摘要（summary）一并返回**：这让「每条结论都能核对」变成**可自动验证的事实** ——
  测试拿它把结论里出现的每一个数字逐个比对（`tests/insight-test.js` 的 `audit()`），
  将来接大模型时它也正好是送进 prompt 的那份输入
- ✅ **界面上不再摆「不调用大模型」的说明块**：原本在顶部有一条说明卡、
  底部有一张「这些结论怎么算出来的」口径卡，按需求**暂时去掉**（代码与本节记录保留）。
  ⚠️ 结论卡片里的**依据列表仍在** —— 那是「数字可核对」的实现，不是「解释为什么不接 AI」，
  去掉它用户就没法核对数字了
- ⚠️ 「试试这样问」这个入口已删除（规则引擎回答不了开放式问题，
  留着一个「你可以随便问」的入口只会误导）
- ⚠️ **笔数少于 3 笔不给任何结论**：一两笔记录说明不了"消费习惯"，
  硬要从中推出「餐饮是最大开支」是过度解读
- ⚠️ **只有「周末明显更高」才说周末**：反过来（周末花得少）没有行动含义，写出来只是凑数
- ⚠️ **涨跌要同时满足比例（≥30%）与绝对额（≥¥100）**：总额 ¥300 → ¥360 涨了 20%，
  只多花 ¥60，把它写成"支出明显上涨"是在制造焦虑
- ✅ 离线自测扩到 **12 个套件**（新增 `insight-test.js`：13 组，重点是**数字审计** ——
  结论里出现的每个金额/笔数/天数都必须能在摘要里找到，多一处就报错）

> 详细取舍与合规背景见「AI 分析接入规划」，那里也写了将来真接大模型时该怎么接。

### v0.7.1（已完成 · 未发布）

这一轮是对全量现有功能做了一遍审查，修掉 4 个真 bug、做 1 处性能优化、补上「关于」页。

- ✅ **「关于」从一行文字改成弹层**：作者 `sneezeee666`、Copyright 说明、邮箱、GitHub 地址。
  ⚠️ 原来用的是 `wx.showModal`：它的正文是死的纯文本，**里面的邮箱和链接既点不了也复制不了**，
  用户只能手抄，而手抄的地址基本都会错。现在邮箱与 GitHub 两行点一下即复制
- ✅ **显示与复制必须是同一个字符串**：作者/邮箱/GitHub 写成 `profile.js` 里的常量，
  由 WXML 绑定渲染、点击时复制常量原文 —— 抄两份的后果是「屏幕上显示的邮箱」和
  「复制出来的邮箱」不一致，而用户几乎不可能发现，只会遇到"发出去的邮件被退回"。
  `tests/static-check.js` 第 19 组校验格式并与 WXML 绑定对账
- ✅ **版权写成「起始年份 - 当前年份」区间**，不写死单一年份：写死 2026 的话，明年这份声明就过期了

**修掉的 bug：**

- 🐛 **账单页切换筛选时列表与空状态会同时出现**：切筛选只清了 `bills` 没清 `groupedBills`
  （旧列表停在新筛选下），而且 `loading` 期间 `firstLoaded` 仍为 `true`、`bills` 已清空，
  于是「这个条件下没有账单记录」会先闪一次再消失 —— 一次查不到数据的假象。
  现在切换时一并清 `groupedBills`，空状态加了 `!loading` 守卫
- 🐛 **导入页去重还没跑完就能点「下一步：确认导入」**：`handleParsedData` 先 `setData` 全量再异步去重，
  这个窗口里 `newBills` 还是未去重的全量，用户抢点就会**重复导入**。
  现在加了 `deduping` 闸门，按钮禁用，`goToConfirm` 与 `confirmImport` 双重校验
- 🐛 **统计页金额被 `Math.round` 抹掉小数**：环形图中心把 `¥8.80` 显示成 `¥9`。
  而且 `>= 10000` 就缩写「万」，与 `utils/format.wxs`「大到一定程度才缩写」的口径不一致 ——
  同一个 App 里两处数字的写法不一样本身就是问题
- 🐛 **Y 轴五档出现重复刻度**：`niceMax` 取到 2.5 时，五档四舍五入后得到 `3 / 2 / 1 / 1 / 0`，
  刻度尺上出现两个 1。`niceMax` 与 `hexToRgba` 抽到 `utils/chart-format.js` 并拆出 `formatAxisAmount`，
  整条轴的单位由 maxValue 一次决定，不再半路换单位（`2.0万 / 1.5万 / 1.0万 / 5000 / 0`）

**性能优化：**

- ⚡ **账单分页不再每翻一页就全表扫描一次**：`buildBillsPage` 原来的 `fetchAll()` 会分页取回该筛选条件下
  的**全部**金额字段来算合计，是这个函数里最贵的一步 —— 翻到第 10 页等于全表扫 10 遍，
  导出账单循环取 20 页就是 20 遍；而合计本身并不会因为翻页而改变。
  现在**只在第 0 页算**，后页的 `totalIncome` / `totalExpense` 返回 `null`，
  前端判断后再写（照抄 null 会把第 0 页算好的汇总冲成 0，汇总条整块消失）。
  ⚠️ **`total`（笔数）依旧每页都给**：它走的是 `count()`，只返回一个数字、不返回文档，代价很小，
  而且是 `hasMore` 的**精确**依据 —— 换成「这一页有没有装满」去推会不准，总数刚好整除时会多请求一次空页

**统一的一处写法：**

- 🔧 「我的」页 `loadUserStats` 的 `if (this.data.loading) return` 闸门改成**请求序号**。
  这个闸门正是账单页顶部明令反对的写法：它把后一次请求直接丢掉，于是下拉刷新看起来"没反应"，
  或者界面停在上一次的数据上

- ✅ 离线自测扩到 **11 个套件**（新增 `chart-format-test.js`：Y 轴刻度不重复 /
  整条轴单位统一 / 小额不被抹成整数 / 与 `format.wxs` 口径一致）

### v0.7.0（已完成 · 未发布）
- ✅ **预算管理**：设一个「每月支出额度」，云端算出**已花 / 剩余 / 还剩几天 / 每天还能花 / 月末预测**，
  并按 **安全（<80%）/ 接近（80~100%）/ 已超（>100%）** 分档。
  额度**一次设置长期有效**，跨月自动沿用 —— 需要每月重设一次的预算，本质上等于没有预算
- ✅ **首页第三格「全部账单」→「预算管理」**，并在首页 hero 卡里直接加了一条**预算进度条**
  （仅在设过预算时出现）。
  ⚠️ 只做一个入口是不够的：「今天还能花多少」是记账产品里最该被一眼看到的数字，
  藏进二级页等于没做 —— 用户不会为了知道超没超而每天点一次
- ✅ **进度条放在 hero 里而不是另起一张卡**：不用把下方的「近 7 天 / 最近交易」整体往下挤
- ✅ **未设预算 ≠ 预算为 0**：从没设过时云端返回 `null`，界面走**设置引导**而不是
  渲染一条 `0 / 0` 的进度条 —— 后者看起来像"额度已经用光"，用户会以为坏了
- ✅ **超支分档的判定用真实比值，不用四舍五入后的百分比**：花了 79.99% 时界面显示的是
  `80%`，若拿显示值去判档，「安全」会被错判成「接近」。`tests/budget-test.js` 专门守这个边界
- ✅ **进度条宽度在云端封顶**（`barPercent`）：**WXML 表达式不能调用函数**（没有 `Math.min`），
  把未封顶的百分比直接塞进 `style="width: x%"` 会让超支时的进度条捅出卡片外
- ✅ **两个入口同源**：首页进度条与预算页走**同一个 `composeBudget()`**，且首页的「已花」
  直接复用 `monthSummary.expense` —— 各算一遍必然出现"首页说还剩 300、预算页说还剩 280"
- ✅ **剩余天数含今天**：今天还没过完，今天的花销仍然算在额度里。分母同样按北京时间算、
  同样显示在界面上（`已过 16 / 31 天`），用户可以自己用「剩余 ÷ 剩几天」核对「每天还能花」
- ✅ **月末预测注明是预测**：写清「按目前速度（日均 ¥75 × 31 天）」，并把算式一起露出来；
  **当月不足 5 天时不给预测** —— 1 号买台冰箱就能推出"本月要花十万"，只会吓到人
- ✅ **未设预算时 `dailyLeft` 为 `null`**：超支后"每天还能花"是负数，没有意义，
  界面改说「已超出 ¥X，先把这个缺口补回来」
- ✅ **hero 卡上的警示色用暖琥珀而不是红**：同一张卡上的红色已经被「本月收入」占用
  （本项目遵循 A 股惯例，收入是红），两种红表示相反的意思谁也分不清
- ✅ **顺手修掉一个隐患**：`utils/user.js` 原来由各调用点自己拼完整档案对象
  （`syncTheme` 只拼 uid/nickname/theme），加字段漏一处就会变成
  「改个主题顺手把预算弄丢了」。改为统一的 `merge(部分字段)`，缺字段一律按"这次没动"处理
- ✅ 离线自测扩到 **10 个套件**（新增 `budget-test.js`：天数分母的月初/月末/闰年/跨零点边界 /
  分档阈值 79.99%~100.01% / 派生数字反向核对 / 两个入口同源 / 前端合并语义）

## ⚠️ 十条关键设计约束（改动前务必先读）

这十条都是踩过坑总结出来的，违反任意一条都会导致「数字看起来不对」「样式静默失效」「删掉别人的数据」或「用户明明填对了却存不上」：

1. **统计聚合必须放云函数。**
   小程序**客户端** `db.collection().get()` 单次最多返回 **20 条**记录。
   在前端 `reduce` 求和会把超出 20 条的记录全部漏掉，金额、占比、趋势全部偏小。
   → 所有汇总/趋势/占比一律走 `getStatistics` 云函数（云端单次可取 1000 条且可分页）。

2. **WXML 没有过滤器语法。**
   `{{ amount | formatAmount }}` 里的 `|` 会被当成**按位或**，小数被静默截断（¥35.50 → ¥35）。
   → 金额/时间格式化统一用 WXS：`<wxs src="../../utils/format.wxs" module="fmt" />` + `{{fmt.amount(x)}}`。

3. **账单时间是北京时间（UTC+8），云函数运行时时区不保证是 UTC+8。**
   → `getStatistics` 里所有「天/月/年」边界都用 `bjTime()/startOfDay()/endOfDay()` 显式计算；
   `parseCSV` 里所有入库时间戳都减去 8 小时偏移。

4. **时间解析失败必须跳过，绝不能用导入时间冒充。**
   微信 xlsx 的「交易时间」是真实日期型单元格，SheetJS 读出来是 Excel 序列号（如 `46310.50909722`），
   不是字符串。`toTimestamp()` 按「数字序列号 / Date 对象 / 日期字符串」三路分发，
   全部失败就返回 `null` 并计入 `skipped`，不写 `Date.now()`。

5. **分类规则必须按收/支作用域隔离（`kind` 字段）。**
   规则表如果混在一起比对，`type:'income'` 的记录会被排在更前面的**支出**规则抢先命中。
   微信退款单的「商品」常常照抄原始商户名（如 `美团` / `外卖订单退款`），
   `'外卖'` 一旦先命中餐饮，一笔收入就被贴上支出分类，在账单页和导出 CSV 里都会显示错。
   → `smartClassify` 里每条规则都带 `kind:'expense'|'income'`，只和当前 `type` 对应的规则比对
   （`tests/add-test.js` 有 14 个探针标题专门守这条线）。

6. **显示时间必须显式按 UTC+8 换算，不能依赖设备时区。**
   `format.wxs` 里所有取值都用 `getDate(ts + 8h)` + `getUTC*()`。
   若写成 `getDate(ts).getHours()`，结果会跟着设备时区漂移——用户出国或改系统时区，
   整份账单的时间会集体偏移几小时。
   （`tests/wxs-test.js` 会用 4 个不同 `TZ` 起子进程，逐字节比对输出是否一致。）

7. **主题令牌不能再套一层「别名」。**
   CSS 自定义属性是在**声明它的那个元素上**完成 `var()` 替换的，替换结果再向下继承。
   把 `--primary-color: var(--brand)` 声明在 `page` 上、再由子元素的 `.theme-xxx` 类重新声明
   `--brand`，`--primary-color` **不会**跟着变 —— 表现为「切了主题，一部分地方变了、一部分没变」。
   → 所有主题令牌直接声明在 `.theme-<id>` 类里（该类挂在每个页面的根节点）；
   `page` 上只放一份默认值当兜底。`tests/static-check.js` 会扫描已废弃的旧变量名。

8. **客户端传来的 `_id` 不可信：删除、修改、读取单条都必须带上 `_openid` 作为查询条件。**
   云函数以**管理员身份**执行，会绕过集合权限 —— 如果写成
   `db.collection('bills').doc(event.id).remove()`，那么任何人构造一个别人的 `_id`
   就能删掉、改掉甚至**读到**别人的账单。正确写法是
   `where({ _id: _.in(ids), _openid: openid }).remove()`，改（`update`）与读单条（`detail`）同理：
   越权的 id 根本查不到，`removed` / `updated` 为 0，前端还能据此如实提示
   "记录已不存在或无权操作"（`tests/delete-test.js` 与 `tests/update-test.js` 分别守这条线）。
   ⚠️ 反过来，`_openid` **绝不能出现在更新字段里** —— 改错它等于把这条记录送给别人。

9. **同一条规则写在前后端两个文件里时，必须让检查工具去对账。**
   昵称长度上下限在 `utils/user.js`（给即时反馈）和 `cloudfunctions/user/index.js`
   （真正说了算的一方）各有一份。两边不一致**不会报任何错**，
   表现是「用户明明填对了却保存失败」—— 而且极难在自己身上复现，
   因为开发者随手填的往往正好是合法值。
   → `tests/static-check.js` 第 18 组会比对两处的 `NICK_MIN` / `NICK_MAX`、
   `BUDGET_MAX` / `BUDGET_DECIMALS`；
   顺带把**云函数 `package.json` 的 `version`** 与 `utils/version.js`、
   以及**本机存储键是否撞车**（两个模块用同一个键会互相覆盖）一起对账。
   同一条思路也用在「关于」信息上：作者/邮箱/GitHub 既要显示又要在点击时被复制，
   抄两份会出现「屏幕上显示的和复制出去的不一致」—— 第 19 组守它。

10. **派生指标（日均、每天还能花…）必须满足三条：分母是"已发生"的量、分母显示出来、在云端算。**
   `平均每天花多少` 这类数字最容易算错，而且错得很隐蔽 —— 分子分母看上去都对，只有商是错的。
   - **分母只能是已经发生的量**：日均 = 总额 ÷ **已过天数**；预算的「每天还能花」= 剩余 ÷ **还剩天数（含今天）**。
     月末按 31 天算会把还没到来的日子算进分母，表现成"看起来花得很少"，会误导用户继续花
   - **分母必须写进界面**：界面上要有「已过 16 天」「还剩 16 天」，用户才能自己用
     `总额 ÷ 天数` 核对。否则这个数字只能靠"相信我们"，而它对用户是真金白银的决策依据
   - **必须在云端算**：客户端按设备时间算天数，在时区被改过或系统时间不准的机器上会悄悄错；
     而且天数必须用 **UTC+8 的「日」相减**（`startOfDay` 之差），不能 `(now - start) / 86400000`
     —— 区间起点是 00:00:00、终点是今天 23:59:59.999，直接相除会**少一天**
   → `tests/test.js` 与 `tests/budget-test.js` 都用**独立算法**验算分母（本月 = 今天的日期数、
   闰年 2 月 = 29 天、跨零点换日），再加一条「日均 × 天数 ≈ 总额」的反向核对。
   把云函数的公式抄进测试等于没测。

## 云函数接口一览

### `parseCSV`

| action | 入参 | 作用 |
|--------|------|------|
| （默认） | `{ fileID, fileName }` | 下载云存储文件 → 解析 xlsx/csv → 返回账单数组 |
| `dedup` | `{ action:'dedup', bills:[...] }` | 对比库中已有记录，只返回需要新增的部分 |
| `delete` | `{ action:'delete', ids:['...'] }` | 删除若干条账单（也接受单个 `id` 字符串）。**条件里带 `_openid`**，越权的 id 删不掉 |
| `clear` | `{ action:'clear' }` | 条件批量删除当前用户全部账单（一次删上千条，避免 3 秒超时） |
| `add` | `{ action:'add', bill:{...}, force? }` | 手动记一笔：校验 → 智能分类 → 服务端写入。返回 `code:2` 表示疑似重复，可用 `force:true` 强制写入 |
| `detail` | `{ action:'detail', id }` | 读单条账单（编辑页预填用）。**条件里带 `_openid`** —— 用 `doc(id).get()` 会漏出别人的记录 |
| `update` | `{ action:'update', id, bill:{...}, force? }` | 改一笔：校验（与 `add` 同一套）→ 重新分类 → **条件带 `_id` + `_openid`** 更新。一条都没改到时 `code:-1` |
| `classify` | `{ action:'classify', bill:{title,product,type} }` | 只做分类预览，不写库（手动记账页输入时实时提示） |

> **删除为什么也叫云函数**：① 云函数写入的文档客户端不一定删得掉（集合权限一旦不是
> 「仅创建者可写」就会被静默拒绝）；② 只有在云函数里才能把 `_openid` 拼进查询条件，
> 保证「只能删自己的」；③ 错误信息统一由云函数 `return`，前端不用区分三种失败原因。
> 前端统一走 `utils/remove-bill.js`（确认弹窗 + 云函数 + 提示一条龙），**两个**入口共用。

> **手动记账为什么也放云函数**：分类规则（`smartClassify`）只有一份，导入和手动录入都调它，
> 不会出现「导入的账分类对、手动的账分类错」这种前后端规则漂移。
> ⚠️ 云函数写入**不会**自动注入 `_openid`，`add` 里必须显式带上，否则 `getStatistics` 查不到这条记录；
> 而 `update` 反过来 —— **绝不能把 `_openid` 写进更新字段**，改错它等于把这条记录送给别人。

> **改一笔的字段取舍**：`category / icon / color` 按新内容**重新识别**（用户改「交易对方」
> 本来就是为了让它归对类）；`_openid / source / orderNo / merchantNo` **一个字都不动** ——
> 改错 `_openid` 等于把这条记录送给别人，`orderNo` 是核对微信账单的唯一凭据。

`bill` 字段：`{ date:'2026-10-15', time:'14:20', type:'expense'|'income', amount, title, product, tradeType, payMethod, status }`
—— 时间由云端用与导入路径相同的 `toTimestamp()` 换算成 UTC+8 时间戳，前后端只维护一套时区逻辑。
`add` 与 `update` **共用同一个 `normalizeManualInput()`**：两边各写一份必然漂移，
最后变成「新增时拦住了负数金额、编辑时却能存进去」这种单向成立的口子。

### `getStatistics`

统计聚合全部在此，**前端不再自己求和**。

| action | 入参 | 返回 |
|--------|------|------|
| `indexData` | — | `{ monthSummary, weekTrend[7], budget }`（含已归一化的柱高 `incomeHeight/expenseHeight`、预算进度块） |
| `stats` | `{ period }` | `{ summary, days, dailyAvg, categories, topCategories, monthlyTrend[6] }` |
| `bills` | `{ period, type, categoryId, page, pageSize }` | `{ bills, total, totalIncome, totalExpense, hasMore }`；⚠️ `totalIncome`/`totalExpense` **只有 `page === 0` 有值，后页是 `null`**（前端据此保留第 0 页的汇总，不覆盖成 0）；`total` 与 `hasMore` 每页都有 |
| `profile` | — | `{ totalBills, totalDays, firstTime, lastTime }` |
| `budget` | — | `{ budget }` —— 预算进度块；**没设过预算是 `null`**（不是 `amount:0` 的对象） |
| `insight` | `days`（可选 `7`/`30`，默认 30） | `{ scope, insights[], summary, meta }` —— 近 N 天规则引擎结论。⚠️ 会员门控由 `INSIGHT_REQUIRE_VIP` 开关控制，**当前为 false（对所有人开放）**；改成 `true` 后非会员返回 `code:-2 + data.needVip` |`insights` 每条含 `id/level/title/detail/evidence[]`，**没有可说的结论时是空数组**（不返回套话）；`summary` 是算出这些结论的完整摘要，界面上不渲染、但测试与将来的 prompt 都用它 |

`period` 取值：`day` | `week` | `month` | `year` | `all`（周一为一周之首；月末/年末截止到「今天」）

**日均收支怎么算**（`stats` 专用，`days` 与 `dailyAvg` 是配套返回的）：

```
days     = 区间起点 → 今天的自然天数（含首尾）   本月 1 号算到 16 号 = 16
dailyAvg = { income: 总收入 ÷ days, expense: 总支出 ÷ days }   各 round 到分
```

- **分母是「已过天数」，不是区间总长度**。`period='all'` 的起点是 1970 年，
  按自然天数算毫无意义 → 此时明确返回 `days: 0` / `dailyAvg: null`，前端据此隐藏整块，
  而不是显示一个「已过 20000 天」
- 天数**必须由服务端计算**：客户端按设备时间算，在时区/系统时间被改过的机器上
  分母会和分子的区间对不上，用户自己一除就发现数字错了
- 计算用 UTC+8 的「日」相减（`startOfDay`），**不能用 `(now - start) / 86400000`** ——
  区间起点是 00:00:00、终点是今天 23:59:59.999，直接相除会少算一天

**预算进度块怎么算**（`indexData` 与 `budget` **共用同一个 `composeBudget()`**）：

```
daysTotal  = 当月自然日数                     31（闰年 2 月自动是 29）
daysPassed = 今天是几号                       16
daysLeft   = daysTotal - daysPassed + 1       16   ← 含今天（今天还没过完）
dailyLeft  = (amount - spent) ÷ daysLeft      超支时为 null
level      = spent > amount ? 'over' : (spent / amount >= 0.8 ? 'near' : 'safe')
```

返回字段：`{ amount, spent, remaining, over, usedPercent, barPercent, level,
daysTotal, daysPassed, daysLeft, dailyAvg, dailyLeft, forecast, forecastOver, updateTime }`

- **`daysLeft` 含今天**（8/16 于 31 天的月份 → 16 天）。不含今天会让「每天还能花」虚高，
  而这个偏高会直接劝退本来可以正常消费的人
- **`barPercent` 是 `usedPercent` 封顶到 100 的结果**，之所以单独返回：小程序
  **WXML 表达式不能调用函数**（没有 `Math.min`），页面拿到未封顶的百分比只能直接塞进
  `style="width: x%"` —— 超支时进度条会捅出卡片外
- **分档用真实比值判定**，不用 `usedPercent`：花 79.99% 时显示的是 `80%`，
  拿显示值去判档会把「安全」错判成「接近」
- **`forecast` 在当月不足 5 天时为 `null`**：1 号买台冰箱就能推出"本月要花十万"，
  这种预测只会吓到人。它是**推测**，界面必须写明「按目前速度」并把算式一起露出来
- 首页的「已花」直接复用 `monthSummary.expense`，不另查一遍账单 ——
  各算一遍必然出现「概览说花了 1200、预算卡说花了 1180」
- 额度存在 `users` 文档的 `budget` 字段里，读写在 `user` 云函数（见下）

### `user`

用户档案（昵称 / 主题偏好 / **每月预算额度**）。**没有注册与登录**：openid 就是身份，
首次调用自动建档，之后所有操作都是更新。

| action | 入参 | 返回 |
|--------|------|------|
| `getProfile`（默认） | — | `{ uid, nickname, theme, budget }`，无档案时自动创建一条空档案 |
| `updateProfile` | `{ nickname?, theme? }` | 更新后的 `{ uid, nickname, theme, budget }` |
| `setBudget` | `{ amount }` | 更新后的同一份档案。`amount` 传 `0` / 空串 = **取消预算** |

- `nickname`：2-12 个 **Unicode 字符**（emoji 算 1 个），自动去首尾空白，
  拒收换行/控制字符，传空串 = 清除昵称
- `theme`：只校验格式（`^[a-z][a-z0-9]{2,15}$`），**不在云函数里维护主题白名单** ——
  那等于再造一份「主题清单」，以后加主题忘了同步，新主题就永远存不进去。
  前端 `utils/theme.js` 的 `normalize()` 会把不认识的 id 安全回落到默认主题
- `budget`：`null` = 没设过；`{ amount, updateTime }` = 已设。金额要求 `> 0`、≤ 1 亿、
  最多 2 位小数（`100.005` **直接拒绝**而不是四舍五入成 `100.01`）。取消预算用
  `db.command.remove()` 把字段删掉，**不留 `0` / `null`** —— 否则「没这个字段」与
  「字段是 null」两种状态并存，以后每个读它的人都要多写一个判断，迟早有人漏
- 返回体只含 `uid` / `nickname` / `theme` / `budget`，**不含 `_openid`、`_id`、时间戳**。
  ⚠️ 这几个字段必须**一起**返回：前端拿到返回体就整份写进本机缓存，少给一个等于顺手抹掉它
  （`utils/user.js` 的 `merge()` 就是为这件事改的，见 `tests/budget-test.js` 的回归断言）
- 更新的 `where` 条件带 `_openid`（与删除账单同一条纪律，见约束 8）

### 安装步骤

1. **克隆或下载本项目**

2. **打开微信开发者工具**
   - 选择「导入项目」
   - 选择 `smart-ledger` 目录作为项目路径
   - 填入你的 AppID（测试号也可以）

3. **配置云开发环境**
   - 在开发者工具中点击「云开发」按钮
   - 创建新的云环境（或选择已有环境）
   - 复制环境 ID
   
4. **修改配置文件**
   
   环境 ID 已配置在 `app.js` 中（当前为 `cloud1-d7gne5bpf2229f19b`）：
   ```js
   wx.cloud.init({ env: 'cloud1-d7gne5bpf2229f19b', traceUser: true })
   ```
   换环境时只改这一处即可。

5. **创建数据库集合**
   
   在云开发控制台的「数据库」中创建集合：
   - `bills` - 存储账单记录（**必须**）
   - `users` - 存储用户档案：昵称 + 主题偏好（**必须**，v0.4.0 起）

   权限**两个集合不一样**（这是有意区分的，不是疏漏）：

   | 集合 | 该选的权限 | 为什么 |
   |------|-----------|--------|
   | `bills` | **仅创建者可读写** | 客户端确实有两处直接操作它：首页「最近交易」是**客户端直查**（`db.collection('bills').limit(10)`），导入页也是**客户端写入**（`db.collection('bills').add`）。账单**列表**反而走 `getStatistics` 云函数。想收得更紧也可以，但要先把这两处也搬进云函数 |
   | `users` | **仅管理端可读写**（控制台也写作「所有用户不可读写」） | 客户端**从不直查** `users`，昵称与主题全部经 `user` 云函数读写。而云函数以管理员身份执行、**绕过集合权限**，所以关掉客户端权限不影响任何功能 |

   > ⚠️ 为什么 `users` 要比 `bills` 更严？
   > 一是**将来这张表要放手机号与密码哈希**，权限一旦放开就很容易忘记收紧，而泄露不可逆；
   > 二是集合权限和云函数里的 `_openid` 条件**是两条独立的防线**：
   > 集合权限只挡得住客户端直查，管不住云函数 —— 真正决定"谁能读到谁"的
   > 是 `where({ _openid: openid })`。两条都做对，才不存在"构造一个 id 就能读别人档案"的口子。
   > 若图省事把 `users` 也设成「仅创建者可读写」，功能照样能跑
   > （云函数写入时已显式带 `_openid`），但等于白白多开一个客户端读口子。
   >
   > 另外注意「仅创建者可读写」有一条**隐式行为**：客户端查询时系统会**自动补上**
   > `_openid == 自己的 openid` 这个条件，更新前也会先按它过滤。
   > 所以那种权限下客户端**读不到别人的数据**，不是靠你自己写对条件。

   ⚠️ 云函数**不会自动创建集合**。`users` 没建的话，第一次调 `user` 函数会返回
   「数据库里还没有 users 集合，请先在云开发控制台「数据库」里新建它」——
   这是有意的，原始报错是 `-502005 database collection not exists`，对用户毫无指示性。
   文档不需要手动建，云函数在首次调用时会自动写入一条空档案。

6. **部署云函数（改动后必须重新部署）**
   
   在开发者工具中右键点击 `cloudfunctions/` 下的文件夹 →
   **「上传并部署：云端安装依赖」**，三个函数都要部署：
   - `parseCSV`（依赖 `wx-server-sdk` + `xlsx`，首次部署较慢，需等依赖安装完）
   - `getStatistics`（依赖 `wx-server-sdk`）
   - `user`（依赖 `wx-server-sdk`）

   ⚠️ 常见坑：
   - `package.json` 的 `name` 必须与文件夹名**完全一致**，否则部署失败；
   - 解析 Excel 用的是 `xlsx`（SheetJS）。换回 `node-xlsx` 会在云端装依赖时失败；
   - 只部署其中一个函数，会出现「改了但没生效」的假象（例如首页对了、统计页还是旧逻辑）。

7. **tabBar 图标**

   `assets/icons/` 下的 45 个 PNG 已经随仓库提供（81×81 的 tabBar 图标 30 个 +
   96×96 的快捷入口/菜单/品牌标识 12 个 + 156×156 空状态插画 3 个），**不需要另找**。
   其中 81×81 里只有 5 个是未选中态（灰色，全主题共用），另外 25 个是
   **5 套主题 × 5 个 tab** 的选中态 —— 因为**原生 tabBar 只能用图片染色**，
   换主题就得换文件。

   ⚠️ **首页三个快捷入口的图标底色不跟主题**：图标是固定色的 PNG，
   底色跟着主题变就会出现「蓝色图标配浅绿底」。所以 `--teal-soft`（预算入口用）
   这类"非主题色"必须是**固定值**，不能用 `--brand-soft`。

   ⚠️ **tabBar 的形状与顺序有三份清单**：`app.json` 的 `tabBar.list`（唯一来源）、
   `utils/theme.js` 的 `TAB_SHAPES`、`tools/gen-icons.py` 的 `TAB_SHAPES`。
   三处顺序不一致**不会报任何错**，只会「点某一栏却亮成另一栏的图标」，
   所以静态检查会比对它们的顺序与项数。加/删栏位时**三个文件都要动**。

   要改主题色：改 `utils/theme.js` 的 `THEMES` → 补 `app.wxss` 的 `.theme-<id>` 类 →
   跑 `python tools/gen-icons.py` 重新生成（脚本自己会读 `theme.js` 取色，不用手填色值）→
   把 `pages/index/index.json` 的 `navigationBarBackgroundColor` / `backgroundColorTop`
   改成新默认主题的 `hero`（首帧还没跑 JS，读的是这两个静态值）。
   `node tests/static-check.js` 会检查这四处是否对得上。

8. **运行项目**
   
   点击开发者工具的「编译」按钮即可预览。改完代码建议先跑一次 `node tests/run-all.js`。

### 改动生效清单（改了统计/解析逻辑后照做）

1. 先跑 `node tests/run-all.js`，14 个套件全绿再继续
2. 重新部署 `parseCSV`、`getStatistics`、`user` —— 只部署一部分会出现「改了一半」的假象
3. 首页 / 账单 / 统计三个页面分别下拉刷新一次

> **只改了主题颜色**的话不用动云函数：改 `utils/theme.js` 的 `THEMES`（`brand` + `hero`
> 两个值）→ 在 `app.wxss` 里补/改对应的 `.theme-<id>` 类（13 个令牌）→
> 跑 `python tools/gen-icons.py` 生成该主题的 tabBar 图标 →
> 改 `pages/index/index.json` 的静态兜底色 → `node tests/static-check.js` 对账
> （四处里任何一处对不上都会直接报错，包括**值不一致**而不只是缺项）。

> **什么情况才需要清库重导？** 只有「账单的 `createTime` 本身是错的」才需要
> （例如曾经用导入时间冒充过交易时间）。
> 单纯改了分类色板、分类名称、统计口径**不需要**清库——
> 展示用的名称/图标/颜色以 `getStatistics.CATEGORY_META` 为准，
> 老记录会直接套用新配色。主题色更是纯本机偏好，与云端数据无关。

### 导入微信账单

1. 打开微信 → 我 → 服务 → 钱包
2. 点击右上角「账单」
3. 点击右上角「...」→ 选择时间范围
4. 选择「导出账单」→ **选 Excel 格式** → 保存到手机
   （导出的文件名形如 `微信支付账单流水文件(20260915-20261015)_20261015130953.xlsx`）
5. 在小程序「导入账单」页点上传，选中该文件
6. 查看解析预览与去重结果（本次新增 / 重复跳过 / 已有记录）
7. 确认导入 → 只写入新增记录，原有数据保持不变

### 手动记一笔

首页「➕ 记一笔」进入录入页：

| 字段 | 说明 |
|------|------|
| 交易时间 | **默认当前北京时间**，可改；点「现在」一键重置 |
| 交易类型 | 下拉，取自真实微信账单的高频取值（商户消费 / 扫二维码付款 / 转账 …） |
| 交易对方 | 文本输入，会参与智能分类 |
| 商品 | 文本输入，会参与智能分类 |
| 收/支 | 分段切换，切换时自动带出更合理的「交易类型 / 当前状态」默认值（手动改过就不再覆盖） |
| 金额(元) | 只允许数字 + 两位小数，保存时四舍五入到分 |
| 支付方式 | 下拉（零钱 / 零钱通 / 储蓄卡 / 信用卡 / 支付宝 / 现金 / 其他） |
| 当前状态 | 下拉，同时覆盖支出与收入两种语境 |

填完「交易对方 / 商品」后会实时显示「将归类到『餐饮』」的预览（失焦后 300ms 防抖请求，
过期响应会被丢弃，所以连续打字不会出现预览闪回）。
**预览和最终入库走的是同一个 `smartClassify`**，保存时云端会重新算一遍，
因此不会出现「预览说餐饮、存进去变其他」的情况。

表单内容改动过却直接返回时会弹一次「这一笔还没保存，确定离开吗？」（保存成功后自动撤掉）。
手动记录的字段结构与导入数据完全一致，因此**可以和导入的账单一起统计**，
测试时靠 `source: 'manual'` 字段区分来源。

> 下拉选项定义在 `pages/add-bill/add-bill.js` 顶部的 `TRADE_TYPES` / `PAY_METHODS` / `STATUS_LIST` 三个数组里，要增删直接改数组即可。

**同一个页面也是「编辑页」**：从账单详情弹层的「编辑」进来会带上 `?id=`，
导航栏标题变成「编辑账单」，原值全部预填，按钮变成「保存修改」。
编辑模式下如果原值不在上面那三个数组里（导入账单的支付方式常是「招商银行(1234)」），
`utils/bill-form.js` 的 `withValue()` 会把它**临时补进选项列表**（追加在末尾）——
不补的话索引会落到第 0 项，保存一次就把用户没动过的字段静默改掉了。
详见「改一笔 / 删掉记错的一笔」。

### 去重规则

以「交易单号」作为主键判重；单号为空时退化为「交易时间 + 金额 + 交易对方 + 收支」组合。
所以**同一份账单反复导入不会产生重复数据**，可以放心地按月份增量导入。

手动记账没有微信单号，会落在「组合键」那一侧——它只可能和自己撞，
不会和导入的账单互相干扰。

另外，手动记账保存前会做一次「同一秒 + 同金额 + 同对方 + 同收支」的重复检测，
命中时弹窗询问，用于拦住「保存成功但网络超时后重试」造成的重复写入。

### 改一笔 / 删掉记错的一笔

| 操作 | 入口 | 适合的场景 |
|------|------|-----------|
| **编辑** | 点开某一笔的详情弹层 → 底部「编辑」 | 金额记错、分类识别错了、想补上商品名 |
| **左滑删除** | 账单页任意一行向左滑 → 露出红色「删除」 | 翻账单时顺手清理 |
| **删除记录** | 点开某一笔的详情弹层 → 底部红色按钮 | 核对完详情后确认删除 |

> 首页曾经有过「减一笔」入口（第三格 → 底部弹层列最近 20 条），v0.4.0 已移除：
> 首页是"看数"的地方，把破坏性动作放在最显眼处容易误触；而账单页能先看到
> 交易对方 / 金额 / 时间，确认成本更低。
>
> 「编辑」和「删除」并排放在详情弹层里，是因为两者共用同一个上下文 ——
> 用户已经在弹层里确认过「就是这一笔」了；而左滑删除是「翻列表时顺手做的事」，
> 留在列表手势里最省事。

**编辑这一侧的取舍：**

- **与「记一笔」是同一个页面**（`pages/add-bill`，带 `?id=` 即进入编辑模式）：
  字段、下拉选项、分类预览、校验规则完全一样。分成两个页面必然漂移，
  最后变成「新增时能填的字段编辑时填不了」
- **原值从服务端重新拉**（`action:'detail'`），而不是从上一页把对象传过来：
  编辑页可能被刷新，列表里的数据也可能是几分钟前加载的 ——
  以服务端当前值为准，才不会出现「基于旧数据改出新旧混搭的字段」
- **原值不在下拉选项里也要保留**：导入账单的支付方式常常是「招商银行(1234)」这种
  带卡号的值，而选项表里只有「零钱 / 零钱通 / 储蓄卡 …」。`utils/bill-form.js` 的
  `withValue()` 会把它补进列表（追加在末尾，不打乱已有下标），否则索引会落到第 0 项 ——
  用户只想改金额，保存一次却顺手把支付方式静默改掉了。
  这种「一处没动过的字段被改掉」最难被发现，也最难被相信
- **什么都不改直接保存，不会弹「疑似重复」**：`hasDuplicate()` 必须排除自己那条，
  否则用户一个字段都没动却被质问，只能困惑地点「仍要保存」—— 这个提示很快就没人看了
- **拉不到原记录就不让编辑**：弹窗说明原因并退出，绝不留一个空表单 ——
  那等于让用户在看不到原值的情况下把整条记录覆盖掉
- **保存后账单页自动重载**：账单页是 tabBar 页，`onShow` 本来就会刷新，
  所以改完回来看到的就是新数据；代价是分页回到第 0 页（与「从记账页返回」的行为一致）
- **改了日期或收支类型也不会「留在原位」**：这类改动会让记录不再满足当前筛选条件，
  本地就地替换很容易算错分组与合计，交给云端重载最稳妥

**删除这一侧的取舍：**

- **必须二次确认**（`wx.showModal`，确认键是红的）。删除不可恢复，一次误触代价太高
- **弹层里连删不关闭**：连着记错两笔时，一次打开就能减完
- **账单页删除后不整页重载**：只把这一条从列表里摘掉并同步修正笔数/收支合计。
  重载会把分页 reset 回第 0 页，用户在第 3 页删一条就被弹回顶部，还会闪一下骨架屏
- **左滑用手势判定而不是"按住就滑"**：先比较横纵位移（4px 内不判定），判定为竖向就
  立刻放弃、把手势还给页面滚动；滑动结束后紧接着的那次 `tap` 会被吞掉，避免误开详情弹层
- **同一时刻只允许一行展开**：某行滑开时会通知父页面，其它行收到 `force-close` 自动收起

### 看统计（含「日均收支」怎么算）

统计页顶部三档切换 **本周 / 本月 / 本年**，「概览」卡自上而下是：

```
结余                         本月至今     ← 区间内总收入 − 总支出
+1,234.56
─────────────────────────────────────
│ 收入 2,000.00    │    │ 支出 765.44
─────────────────────────────────────
日均收支                       已过 16 天   ← 分母显示出来，方便自己核对
日均收入 125.00      │    日均支出 47.84
```

- **日均 = 区间总额 ÷ 已过天数（含今天）**，不是 ÷ 区间总长度。
  所以 10 月 16 号看「本月」，分母是 16；看「本年」，分母是今年第 289 天
- 分母直接写在界面上（`已过 N 天`），是为了让这个数字**可被核对**：
  总支出 ÷ 天数 应该正好等于显示的日均
- 分母由云端给出（与区间起止是同一次计算），**不要改成前端自己按设备时间算** ——
  时区或系统时间被改过的机器上会算错，而且错得很隐蔽
- 某段时间没有任何记录时，日均显示 `0.00`（不是空白也不是 `--`），
  因为「这段时间没花钱」本身就是一个有效结论

### 设预算 / 看超支（v0.7.0）

入口有两个，都进同一个页面：

| 入口 | 位置 |
|------|------|
| **首页第三格** | 「预算管理」（原先这里是「全部账单」——账单本来就在 tabBar 上，不差这一个入口） |
| **首页 hero 里的进度条** | 「本月结余」下面那条，**只在设过预算时才出现**；点它直接进预算页 |

设一个每月支出额度（比如 3000），之后：

```
每月预算                              额度内
本月已花
¥1,234.56
每月预算 ¥3,000.00
```

**额度是「每月固定额度」，跨月自动沿用** —— 设一次就行，不用每月 1 号重设。
想改随时改，想取消点「取消预算」。

几个刻意的取舍：

- **一次设置长期有效**：个人记账的习惯是「我每月预算 3000」，而不是「10 月 3200、11 月 2800」。
  按月存一条会逼用户每月维护一次，忘了就退回"没有预算"状态 —— 需要每月维护的预算等于没有预算
- **超支分三档**：安全（已用 <80%）/ 接近（80~100%）/ 已超（>100%）。
  阈值只定义在 `getStatistics` 一处，前端不复制 —— 两处各写一套必然出现
  「首页说安全、预算页说接近」，而且改了一处忘另一处不报任何错
- **「还剩天数」含今天**：今天还没过完，今天的花销仍然算在额度里。
  不含今天会让「每天还能花」虚高一点，而这个偏高会劝退本来可以正常消费的人
- **超支后不再显示「每天还能花」**：剩余为负时"每天还能花"是个负数，没有意义；
  界面改说「已超出 ¥X，先把这个缺口补回来」
- **月末预测会明确标注是预测**：写「按目前速度」并把算式露出来（日均 × 当月天数）。
  **当月不足 5 天时干脆不给预测** —— 1 号买台冰箱就能推出"本月要花十万"，只会吓到人
- **没设过预算时不显示进度条**，而是显示设置引导。绝不渲染一条 `0 / 0` 的进度条：
  那看起来像"额度已经用光"，和"还没设过"完全是两件事
- **超支不用红色**（首页 hero 卡上）：同一张卡上的红色是「本月收入」的意思（A 股惯例，红为进），
  两种红表示相反的事谁也分不清 → hero 上的警示统一走暖琥珀，超支与接近的区别交给文案。
  预算页是白底、且页面上没有收入数字，那里才用红色

检测规则（各自不满足条件就不出现）：

| 规则 | 什么时候出现 |
|------|-------------|
| 预算进度 | 已用 ≥80%、已超支，或按当前速度预测会超（**复用首页那套预算口径**） |
| 月光预警 | 支出进度远超时间进度（如本月过半已花 80%），按当前速度外推「几号花光预算」 |
| 日均涨跌 | 平均每天支出与上一个同长周期相比涨/跌 ≥30% **且**日均差额 ≥¥5 |
| 消费结构 | 某个类目占总支出 ≥35%（且至少有两个类目可比） |
| 深夜消费 | 23:00 ~ 凌晨 05:00 的支出占总支出 ≥10% |
| 大额支出 | 单笔超过「月均支出 20%」或「¥500」（两者取高），并注明主要集中在哪个类目 |
| 小额高频 | 单笔 ≤¥20 的有 ≥8 笔，且合计占总支出 ≥8% |
| 常去的地方 | 单一商户占总支出 ≥25% |
| 周末效应 | 周末日均比工作日高 ≥50% **且**差 ≥¥20 |
| 记账连续性 | 末尾连续 ≥4 天没有支出（可能是漏记） |

外加一条**基准**（该窗口共花多少、日均多少、几笔）。

> ⚠️ **条数会随数据变化**，不是固定几条。规则不满足条件时就是空数组，
> 界面会说"这 N 天没有值得说的异常"。少于 3 笔记录时同样不给结论 ——
> 两三笔说明不了"消费习惯"，硬要推出结论是过度解读。
>
> ⚠️ **「支出涨跌」用日均而不是总额比**：总额比较要求两个周期都是满的（比如都满 30 天），
> 但账龄短的用户「前 30 天」有一半是空的，比总额没意义。日均天然摊平了天数差异。
>
> 原生 tabBar 官方上限是 **5 项**（2~5，超了直接编译失败），所以这是最后一栏，
> 以后要再加页面只能走「更多」聚合页或改造自定义 tabBar。

## AI 分析接入规划（v1.0.0）

> 以下官方信息核对于 **2026-10**。模型 id 与 provider 名在不同版本的文档里并不一致
> （`deepseek` / `cloudbase` 都出现过），**以自己控制台「AI → 生文模型」里实际启用的模型为准**。

### 第 0 步：合规先于技术（这条决定能不能上线）

微信对"AI 问答"有明确且从严的类目要求，**这不是技术问题，是主体资质问题**：

| 主体 | 能不能上线 AI 功能 |
|------|-------------------|
| **个人主体** | ❌ **不能**。官方口径：「AI 问答涉及深度合成技术，需补充【深度合成-AI 问答】服务类目；**目前个人主体小程序尚未开放深度合成相关服务类目**，建议申请企业主体」。已有多个个人主体小程序因"涉及 AI 问答"被要求整改 |
| **企业主体** | ✅ 可以，但需三步：① 企业认证 ② 算法备案（云开发 AI+ 概览页可**自助生成备案资料**）③ 加【深度合成-AI 问答】类目并上传《深度合成服务在用证明》（须含主体名称、AppID、订单有效期、算法备案号） |

⚠️ 两个容易踩的坑：

1. **"AI 小程序成长计划"不等于"可以上线 AI"**。成长计划（MP 后台 → 行业能力 → AI 小程序成长计划）
   个人与企业主体都能报名、都能拿到 10 亿 Token 额度（2026-07-01 ~ 12-31 有效），
   但官方同一篇公告里写明：**"当前平台未开放个人开发者备案【深度合成】类目权限，
   个人开发者可上架与大模型交互无关的线上工具小程序"**。额度是给你开发和测试用的，不是上线许可证。
2. **审核以实际运行内容为准**，不看代码注释。提审时的「功能描述」要写清技术实现方式，
   官方明确建议这么做以避免误判（有人靠"在功能描述里说明实现方式"通过了审核）。

由此有两条现实路线：

| 路线 | 做法 | 合规性 | 适合 |
|------|------|--------|------|
| **A · 不与大模型交互** | AI 分析做成**固定输入→固定输出**的规则引擎：云端算异常检测 / 省钱建议 / 预算预测，**不接模型、不做对话** | ✅ 无风险，个人主体可上线 | 正式发布 |
| **B · 真接混元/DeepSeek** | 按下面的技术方案接入，`pages/ai` 的入口用**编译期开关**控制，正式版关闭 | ❌ 个人主体不可上线 | 企业主体 / 体验版自用 |

⚠️ 路线 A 与 B 的差别**不在代码量，而在"有没有自由输入框"**：
「让用户随便问」= AI 问答（要资质）；「把用户自己的账单算出一份固定结构的结论」= 数据加工。
后者仍然属于生成式内容的边界地带，所以**正式发布时建议走 A**。

### 官方提供的三条路径（都已核实）

**方式一：SDK 直接调模型**（免密钥，本项目若要接就用这条的上游）

```js
// 小程序端（基础库 ≥ 3.7.1 才有 wx.cloud.extend.AI）
const model = wx.cloud.extend.AI.createModel('deepseek')
const res = await model.streamText({
  data: {
    model: 'deepseek-r1',                       // 具体模型版本，以控制台启用列表为准
    messages: [
      { role: 'system', content: systemPrompt },
      { role: 'user', content: summaryJSON }    // ← 这里送的应该是账单**摘要**
    ]
  }
})
for await (const chunk of res.textStream) {
  // 原生流式，逐块追加到界面即可
}
```

- **不需要 API Key**：密钥由 CloudBase 平台托管
- **不需要配 request 合法域名**：走云开发内部通道，不受小程序域名白名单限制
- **流式是原生的**，不用自己处理 SSE / ArrayBuffer
- 也支持 `generateText()` 非流式一次性返回

**方式二：云开发 Agent**（`wx.cloud.extend.AI.bot.sendMessage({ botId, msg, history })`）。
控制台建 Agent 后拿 `botId`，自带提示词、知识库、历史记录、次轮问题推荐。
⚠️ 这就是**多轮对话**——正是个人主体过不了审的那种形态。

**方式三：官方 AI 对话组件**（`components/agent-ui`，`type: 'bot' | 'model'`）。
省掉聊天界面，但同样是对话形态，合规性质与方式二相同。

费用：AI 能力新用户首月免费 + 赠 100 万 token；成长计划的 AI 资源包额度更高（见上文路线表）。

### 为什么仍然建议包一层自己的云函数

官方 SDK 允许前端直连（且免密钥，这确实省事），但本项目仍建议走 `aiAnalyze` 云函数：

| 原因 | 说明 |
|------|------|
| **统计数据本来就在云端** | 客户端 `db.collection().get()` 单次最多 20 条，摘要必须复用 `getStatistics` 的 `periodRange()` 与聚合口径，顺路就有 |
| **模型不产出数字** | 结论里的每个金额都要由云端算好再下发，让模型只负责"怎么组织语言"。这要求送进去的摘要、校验回来的数字都在同一个可信执行点 |
| **缓存与限流** | 缓存键要用"账单条数 + 最新 `createTime`"这种数据指纹，这些都得云端算 |
| **可随时关掉** | 开关放云端环境变量，正式版关掉入口而不必改前端逻辑 |

计划新增云函数 **`aiAnalyze`**（第 4 个），入参 `{ period, question? }`，出参是一份**结构化结论**。

### 数据流（关键：送摘要，不送明细）

```
pages/ai ──period──▶ aiAnalyze 云函数
                        │
                        ├─ 1. 复用 getStatistics 的 periodRange() 与聚合口径，算出「摘要 JSON」
                        │      （总额、分类占比 TOP N、日趋势、环比…；不含逐笔交易对方）
                        ├─ 2. 拼 prompt → 调模型
                        └─ 3. 校验 + 回算 → 返回结论数组
```

**为什么只送摘要、不送原始明细**：① 省 token（近 30 天可能上千笔）；
② 逐笔明细里有交易对方（真人姓名、商户），外发面越大隐私风险越高。
摘要只保留聚合后的类别与金额。

### 提示词与输出约束

- **system**：角色设定（个人财务分析师）+ 输出必须是 **JSON**（而不是自由散文），
  每条结论带 `title` / `detail` / `evidence`（引用的数字）
- **user**：结构化摘要 JSON + 用户的自定义问题（`question` 可为空）
- **硬约束写进 prompt**：*"只能引用输入里出现的数字，不要自己计算或推测新数字"* ——
  否则模型会编出看起来很合理的金额
- ⚠️ **但 prompt 里的约束只是"请求"，不是"保证"**。它拦不住幻觉，只能降低概率，
  所以下一节的回算校验是**必须做**的，不是可选的

### 数字可信度（本项目最在意的一条）

模型输出的**每一个数字**，前端都要对照摘要**回算一次**；对不上就降级为
「仅供参考」的弱提示，或干脆不展示这一条。
理由和「日均收支要把分母显示出来」是同一条铁律 —— **派生数字必须可核对**，
而模型恰恰是最容易在不报错的情况下把数字写歪的一环。

实现上最省事也最稳的做法：**结论卡片里的金额根本不由模型给出**。
云端先把每个数字算好塞进 `evidence` 字段（`{label:'本月餐饮支出', value:1234.56}`），
模型只负责写 `title` 和 `detail` 这两句人话，界面上的数字直接渲染 `evidence`。
这样模型根本没有机会改数字 —— 比"校验它有没有算错"更彻底。

### 缓存与成本

- 缓存键 = `period` + **数据指纹**（账单条数 + 最新 `createTime`）+ 问题文本 hash，
  24 小时内复用结论；连点按钮不会重复计费
- 数据指纹一变（新导入 / 新记一笔）缓存自然失效 —— 不需要手动清理

### 失败与降级

- 模型超时 / 报错 / 返回非法 JSON → **退回规则版结论**（路线 A 的那套确定性计算），
  并在界面标注「本次为规则版分析」。这比弹一个"分析失败"有用得多：
  用户点按钮是为了拿到建议，不该因为模型抽风就什么都拿不到
- ⚠️ **但绝不返回一条"兜底的模型结论"** —— 返回假结论比返回失败危险得多。
  降级到的是**真算出来的规则结论**，不是编出来的
- 接入后 `pages/ai` 的空状态与按钮文案会被替换，但**空状态本身要保留** ——
  用户第一次进来、还没有任何账单时依然要看到一个正常的空状态
- 成本兜底：每个 openid 每天最多 3 次真实模型调用，超出后直接走规则版

### 合规与标识（路线 B 适用）

- 走 CloudBase 内置通道**不需要配 request 合法域名，也不需要自己持有 API Key**
  （密钥由平台托管）；若改走第三方 OpenAI 兼容接口，则云函数需能出外网，
  且密钥必须放云函数环境变量，**绝不能进小程序包**（包可被解包）
- 模型输出必须过敏感词；界面要标注 **「内容由 AI 生成」**
  （《生成式人工智能服务管理暂行办法》要求对生成内容作标识）
- 需要在小程序后台的「用户隐私保护指引」里补充「账单数据用于 AI 分析」的说明，
  并在**首次使用前**弹窗告知：会发送哪些字段（只有聚合摘要）、发给谁、可以不用
- 企业主体另需：算法备案 + 【深度合成-AI 问答】服务类目（见「第 0 步」）

## 核心代码说明

### 账单解析 (`cloudfunctions/parseCSV/index.js`)

1. 从云存储下载文件 buffer（或用 base64）
2. `.xlsx/.xls` 走 SheetJS；`.csv` 走文本解析；未识别时先试 Excel 再试 CSV
3. **扫描前 25 行找表头**（微信账单前面有 16 行说明文字），命中条件：同时含「交易时间」和「收/支」或「金额」
4. 字段映射：`收/支`→type、`金额(元)`→amount、`交易对方`→title、`商品`→product、`交易单号`→orderNo
5. 时间解析 `toTimestamp()`：Excel 序列号 / Date 对象 / 日期字符串三路分发，失败返回 `null` 并跳过
6. 关键词智能分类（14 组规则，按 `kind` 隔离收/支）→ 输出 `{ title, type, amount, category, categoryId, icon, color, createTime }`

### 智能分类规则 (`smartClassify`)

导入和手动记账**共用这一个函数**，所以两条路径的分类结果不会漂移。

```js
function smartClassify(title, product, originalCat, type) {
  const text = (title + ' ' + product + ' ' + originalCat).toLowerCase()
  const want = type === 'income' ? 'income' : 'expense'
  for (const rule of rules) {
    if (rule.kind !== want) continue          // ← 关键：只和同侧规则比对
    if (rule.kw.some(k => text.includes(k.toLowerCase()))) {
      return { id: rule.id, name: rule.name, icon: rule.icon, color: rule.color }
    }
  }
  return want === 'income' ? 其他收入 : 其他支出   // ← 兜底
}
```

- **匹配文本** = `交易对方 + 商品 + 原始分类`，统一转小写后做子串包含
- **顺序即优先级**：数组从上到下、命中即返回（支出 8 条 → 收入 6 条）
- **作用域隔离**：`kind` 必须等于当前 `type`，否则收入会被支出规则抢走
- **无命中兜底**：按 `type` 落到 `other_income` / `other_expense`，绝不会留空

色板必须与 `getStatistics` 里的 `CATEGORY_META` **保持一致**（云函数之间无法共享模块，只能人工同步）。
展示时以服务端的 `CATEGORY_META` 为准，所以**改色板后老数据不需要清库重导**，
`tests/test.js` 里专门有一条断言守着这个行为。

### 手动记账与编辑 (`cloudfunctions/parseCSV/index.js`)

`addManualBill` / `updateManualBill` 和导入**共用同一份 `smartClassify` 规则和同一个
`toTimestamp` 时间换算**，所以三条写库路径产出的文档结构完全一样，统计侧不需要区分来源。

- 校验：金额 > 0 且 ≤ 1 亿、不接受负数、日期必须能解析成合法时间（13 月 / 2 月 30 日会被回环校验拦下）
- ⚠️ **校验规则只有一份**（`normalizeManualInput()`），新增与编辑都调它。
  两边各写一份必然漂移，最后变成「新增时拦住了负数金额、编辑时却能存进去」
- 疑似重复：`同一秒 + 同金额 + 同对方 + 同收支` 已存在时返回 `code:2`，
  前端弹窗确认后可 `force:true` 强制写入。**编辑时排除自己那条** ——
  否则「什么都不改直接保存」会命中自己，用户被莫名其妙的「疑似重复」拦一次，
  这个提示很快就没人看了
- ⚠️ `add` 必须把 `_openid` 显式写进文档（云函数不会自动注入，漏了就统计不到）；
  `update` 正相反 —— **绝不能把 `_openid` 写进更新字段**，改错等于把这条记录送给别人
- 编辑的 `where` 同时带 `_id` 与 `_openid`；读单条（`detail`）也一样，
  **不能用 `doc(id).get()`**：它不带条件，而云函数以管理员身份执行、绕过集合权限，
  会漏出别人的记录
- 编辑时 `category / icon / color` 按新内容重新识别，`source / orderNo / merchantNo` 保留原值

### 统计聚合 (`cloudfunctions/getStatistics/index.js`)

- `fetchAll()` 以 1000 条/页分页取全量，绕开单次条数上限
- `bjTime() / startOfDay() / endOfDay()` 显式按 UTC+8 计算边界
- `countDays()` 算「已过天数」作日均的分母（见「云函数接口一览」里的口径说明）
- `daysInMonth()` 用 `Date.UTC(y, m+1, 0)` 取当月最后一天 —— 闰年 2 月自动是 29，不用写死
- `composeBudget()` 是**纯函数**（不碰数据库），所以 `indexData` 与 `budget` 两个 action
  能共用它、离线测试也能直接调它。首页那边把已经算好的本月支出直接传进去，
  不为了预算再查一遍账单
- 首页 7 天趋势的柱高在云端归一化到 0~160rpx（`CHART_HEIGHT`），前端只负责渲染

### 预算管理 (`cloudfunctions/getStatistics` + `pages/budget/`)

规则只有一处：**所有数字都在云端算完再送下去**，页面一个算式都不写。

```js
// cloudfunctions/getStatistics/index.js
const BUDGET_NEAR = 0.8          // 花到 80% 起算「接近」（前端不复制这个阈值）
const FORECAST_MIN_DAYS = 5      // 当月不足 5 天不给月末预测

const ratio = amount > 0 ? used / amount : 0                        // ← 判定用真实比值
const level = used > amount ? 'over' : (ratio >= BUDGET_NEAR ? 'near' : 'safe')
const usedPercent = Math.round(ratio * 100)                         // ← 只用于显示
const barPercent = usedPercent > 100 ? 100 : usedPercent            // ← 提前封顶，WXML 没有 Math.min
```

前端只做三件事：`utils/user.js` 负责额度的读写与本机缓存（首帧同步可读），
`pages/index` 渲染 hero 里那条进度条，`pages/budget` 渲染详情与设置。
**分档文案**（额度内 / 接近额度 / 已超支）由页面翻译，但**分档本身**由云端给 ——
阈值放在两处，迟早出现「首页说安全、预算页说接近」。

`utils/user.js` 里还有一个值得单独说的改动：档案缓存从「各调用点自己拼完整对象」
改成了统一的 `merge(部分字段)`。

```js
// 早期写法（setNickname / syncTheme 各拼一份）
writeStorage({ uid: ..., nickname: ..., theme: ... })   // ← 加 budget 字段就得改两处，漏一处就丢数据

// 现在：缺字段一律按"这次没动"处理
merge({ theme: r.data.theme })                          // ← budget / nickname 原样保留
```

### 图表 (`pages/stats/stats.js`)

用 **Canvas 2D**（`<canvas type="2d" id="...">`）绘制，而不是废弃的 `wx.createCanvasContext`：

- 通过 `createSelectorQuery().fields({node:true, size:true})` 拿节点
- 按 `pixelRatio` 放大 `canvas.width/height`，再 `ctx.setTransform(dpr,0,0,dpr,0,0)`
  —— 不做这一步，在 2x/3x 屏上线条和文字会发虚
- **环形饼图**：支出分类占比，中心显示「总支出」；点图例可高亮某一类（其余扇区 `globalAlpha` 压暗）
- **柱状图**：各类别金额对比（纯 WXSS 渲染，非 canvas，所以能直接吃 `item.color`）
- **折线图**：近 6 个月收支趋势，虚线网格 + 渐变面积填充 + 环形数据点

> ⚠️ **所有图表上的数字都走 `utils/chart-format.js`**（`formatAmount` / `formatAxisTick` /
> `niceMax` / `hexToRgba`），页面里不再各写一份。v0.7.1 之前这几个函数是 `stats.js` 的局部函数，
> 出现过两个 bug：环形图中心用 `Math.round` 把 `¥8.80` 显示成 `¥9`；
> `niceMax` 取到 2.5 时五档四舍五入后出现两个 1（`3 / 2 / 1 / 1 / 0`）。
> 抽成纯函数是为了能被 `tests/chart-format-test.js` 离线钉住。
> 另外**整条轴的单位由 `maxValue` 一次决定**，不逐个刻度各自判断 ——
> 半路换单位（`2.0万 / 1.5万 / 5000 / 0`）比数字不准更难看。

### 智能分析页 (`pages/ai/` + `cloudfunctions/getStatistics/lib/insight.js`)

**规则引擎版，不接大模型**（个人主体无法上线 AI 问答类功能，见「AI 分析接入规划」第 0 步）。

### 为什么规则引擎比模型更适合这里

| | 模型 | 规则引擎 |
|---|---|---|
| 数字准不准 | 会编。prompt 里写「只能引用输入里的数字」只是**请求**，拦不住 | 每个数都是算出来的 |
| 没话说的时候 | 总能生成点什么 | **返回空数组**，界面显示"这 30 天没什么值得说的" |
| 可核对 | 要额外做回算校验 | 天生可核对（依据直接摊开） |
| 能不能上线 | 个人主体 ❌ | 个人主体 ✅ |

### 规则引擎的形状

```
index.js  buildInsightData(days)
   ├─ 取「近 N 天 + 上一个 N 天」的账单（fetchAll，N ∈ {7, 30}）
   ├─ 组装 summary（纯数据：总额/类目/商户/日均/周末/连续无支出/深夜/大额/预算进度）
   └─ insight.buildInsights(summary)   ← 纯函数在这里
          ├─ 10 条检测规则，不满足条件就返回 null
          ├─ 每条产出 { id, level: warn|tip|info, title, detail, evidence[] }
          └─ 按 level 排序后取前 6 条
```

⚠️ **规则引擎必须是纯函数**（不查库、不碰 wx，只吃 summary）——
这样 `tests/insight-test.js` 才能把每条规则的触发/不触发边界离线跑一遍。
代价是摘要组装要写在 `index.js` 里，不能和规则混在一起。

### 几个刻意的做法

- **每条结论都带 evidence**：合计、占比、笔数、天数逐项列出。
  没有依据的结论用户只能"相信我们"，而它会影响真金白银的决策
- **`analyzed` 与 `insights.length` 是两回事**：
  前者表示"点过按钮"，后者表示"有几条结论"。四种状态（未点/加载中/失败/无结论）
  各有各的界面，不能混 —— 把"分析不出东西"显示成"分析失败"会让人以为功能坏了
- **失败时清空旧结论**而不是留着上一份：账单已经变了却展示旧分析，
  比什么都不显示更糟 —— 用户会照着旧结论做决定
- **用请求序号而不是 `if (analyzing) return`**：后者把后一次请求直接丢掉
- **`LEVEL_TEXT` 在 JS 里预先映射**：WXML 表达式不能调用函数，也没有可用三元
- **hero 卡复用与首页、我的同一组令牌**（`--hero-top/-grad/-glow/-sh-hero`）；
  主题接线用 `theme.attach(this, true)`，并在 `onShow` 里 `getTabBar().setData({ selected: 3 })` ——
  ⚠️ 这个 index 必须与 `app.json` 里 `tabBar.list` 的顺序一致，插栏位后「我的」变成了 4

### 设计系统 (`app.wxss`)

一套 CSS 变量贯穿全站，页面只写布局、不硬编码颜色：

| 类别 | 变量 |
|------|------|
| 品牌（**随主题**） | `--brand` `--brand-dark` `--brand-soft` `--brand-soft-2` `--brand-grad` `--nav-grad` `--brand-line` `--sh-brand` `--sh-brand-soft` |
| 深色 hero（**随主题**） | `--hero-top` `--hero-grad` `--hero-glow` `--sh-hero` |
| 深底文字（**不随主题**） | `--on-hero` `--on-hero-dim` `--on-hero-income` `--on-hero-expense` |
| 收支语义（**不随主题**） | `--income`(红) `--expense`(绿) 及 `-soft` 变体 |
| 点缀 | `--accent` `--violet` `--amber` |
| 皮肤 | `--surface`/`-2`/`-3`、`--line`/`-strong`、`--ink-1`~`-4` |
| 形状 | `--r-sm/md/lg/xl/pill`、`--sh-1/2` |

- 组件里**不要用 `:last-child`**：组件根节点是自己影子树里唯一的孩子，` :last-child` 恒为真。

- 自定义导航栏的页面（`pages/import`）**必须用通栏容器**：全局 `.container` 带 `padding: 24rpx`，
  会把导航栏左右和上方顶开 24rpx，露出一圈浅色底（就是那个「白边」）

### 主题色系统 (`utils/theme.js`)

```
utils/theme.js  THEMES  ←─ 唯一数据源（id / 名称 / brand / hero）
      │
      ├─→ app.wxss  .theme-<id> { 13 个令牌 }        ← 静态检查对账（含值，不只是存在性）
      ├─→ assets/icons/*-active-<id>.png            ← tools/gen-icons.py 生成
      ├─→ 每个页面根节点 class="... theme-{{theme}}"  ← theme.attach(this) 写入
      └─→ wx.setNavigationBarColor（只有首页用）      ← theme.syncNavBar()
```

- 切换入口：**我的 → 设置 → 主题颜色**（底部弹层选色板），即时生效并写入 `wx.setStorageSync`
- 默认主题 **微信绿 `#07C160`**；`page` 上另放一份默认值，兜住「根节点还没挂上类」的那一帧
- **深色 hero 卡片跟主题走**（首页顶部概览卡、「我的」顶部品牌卡共用同一组令牌）。
  做法不是把品牌色直接调亮，而是在同色系里取**中深饱和**色。三条取值标准：
  ① 白字对比度 ≥ 6.5:1（卡片上有 68rpx 的结余大数字）；
  ② 同色的灰白小字（`--on-hero-dim`）在渐变末档上也要 ≥ 4.5:1，所以透明度取 0.78 而不是 0.66；
  ③ 渐变三档的亮度比 ≤ 1.3 —— 跨度一大就变成廉价的塑料渐变（早先用过 L≈6% 的墨色，
  在白底页面里像一块黑补丁，用户反馈「太深、渐变很明显」，已按上述标准改过一轮）。
  橙色提亮后是偏暖的**烧褐**，不是浅橙（浅橙大面积铺底既刺眼又和「收入红/支出绿」抢注意力）
- **原生导航栏 / tabBar 只能用图片文件和 JS 接口染色**，CSS 变量够不着，所以各有一套：
  - tabBar 图标：按主题预生成（**5 个 tab × 5 套 = 25 个 PNG** + 5 个全主题共用的未选中态），运行时用 `wx.setTabBarItem` 换
  - 导航栏：首页 hero 是顶到导航栏下面的，两者必须**同色**，否则中间会露出一条色差带。
    颜色由 `theme.syncNavBar()` 用 `--hero-top` 的同值调 `wx.setNavigationBarColor` 设置；
    下拉刷新露出的顶部底色也一并同步（只染顶部 —— 底部过度滚动仍用页面底色，不然像页面漏了一块）
  - 两处都用「已同步标记」避免每次 `onShow` 重复调用；**接口 fail 时不打标记**，这样回到页面会自动重试
- 只有**首页**用深色导航栏，账单/统计/AI/我的都是白底黑字 —— 所以 `attach` 的第三个参数
  （`withNavBar`）只有首页传 `true`。在这四个页面上调 `syncNavBar` 会把导航栏莫名染深
- 收/支语义色（红/绿）**不跟主题走**：它们是金融含义，不是品牌表达。
  但正因为 hero 现在会变成绿色，「支出绿」与主题绿的区分就靠 `--on-hero-expense` 那一档亮薄荷
  —— 5 套 hero 都是深色，同一组浅色值在所有主题上都够对比度，所以这组只在 `page` 上声明一次

### 登录与用户体系 (`utils/user.js` + `cloudfunctions/user/index.js`)

**这个应用没有登录页，也不应该加。** 身份由云开发在云函数侧隐式提供：

```js
const openid = cloud.getWXContext().OPENID   // 微信签名，客户端伪造不了
```

它免授权、零成本、无密码可泄露，本身就是一套比「手机号 + 密码」更省事的登录。
所以「账户」这一层只做一件事：**把用户档案和 openid 对上**，并存昵称与主题偏好。

**两层结构**（和主题系统同一套模式）：

| 层 | 作用 | 为什么需要 |
|----|------|-----------|
| 本机缓存 `wx.setStorageSync('app_user_profile')` | 首帧**同步**读 | 页面第一帧就要有名字。只读云端的话，用户会看到昵称「先空一下再出现」 |
| 云端 `users` 集合 | 权威值 | 换设备 / 重装后能恢复昵称与主题；也是将来多端绑定的落点 |

启动流程：`app.js` 的 `onLaunch` 调 `user.load()` 把云端值拉回本机 →
若云端存过主题偏好，`user.adoptRemoteTheme()` 把它落到本机并立即生效。
页面 `onShow` 先读缓存渲染，云端结果回来后再纠一次（本机已有值，多数时候没有可见跳变）。

**数据表**

```
users {
  _id: uid            // 随机生成，不是 openid
  _openid: '...'      // 云函数写入时必须显式带上（不会自动注入）
  uid: 'u<18位hex>'   // 与 _openid 分开，为将来「一个人的第二个微信」留路
  nickname: ''        // 显示名，2-12 字符，可重名
  theme: ''           // 主题偏好；空串 = 没设过，前端保留本机选择
  budget: null        // 每月支出额度；null = 没设过，{ amount, updateTime } = 已设
                      // ⚠️ 取消预算用 _.remove() 把字段删掉，不留 0 ——
                      //    「没这个字段」和「字段是 null」两种状态并存，迟早有人漏判断
  createdAt, updatedAt
}
```

> **`budget` 为什么也放这张表、而不新开一个 `budgets` 集合？**
> 当前需求是「每月一个总额度」= 一个数字。为它单开一个集合，只为了存一个数：
> 多一次手动建集合的部署步骤（云函数不会自动建集合），多一套 upsert 逻辑
> （同一周期只能有一条），却换不来任何东西。它和昵称、主题一样是"跟着账号走的偏好"，
> 放在同一份档案里、由同一个云函数读写，反而更不容易出岔子。
> 将来若真要做**分类预算**（餐饮/购物各一条，**目前不在计划内**），多行结构才有意义，那时候再迁到独立集合
> —— 迁移成本很低（读一个数、写若干条），而现在的复杂度是实实在在的。

> ⚠️ **为什么 `uid` 不和 `openid` 合一？**
> 现在所有账单按 `_openid` 隔离，够用。但一旦要支持「同一个人换微信 / 多设备看同一份账本」，
> openid 就会把一个人劈成两个账号。`uid` 独立出来后，`users` 表只需多挂一个 openids 数组即可
> 平滑扩展，**不用迁移这张表**。
> 真正要迁移的是**账单表**（加 `uid` 字段 + 刷历史数据 + 把账单列表查询从客户端直查收口进云函数）——
> 那是另一条路线的代价，详见下节。

**关于「手机号 + 密码」**

个人主体小程序**用不了官方的手机号快速验证组件** —— 该能力仅对
**非个人主体且已完成微信认证**的小程序开放，且自 2023-08-28 起按 **0.03 元/次**收费
（每个账号 1000 次体验额度）。所以在本项目当前的主体类型下，
「手机号登录」只能退化成「让用户手输一个手机号、不做运营商验证」，
它既不能证明身份，也就没法承担「找回账号」的职责 —— 收益很有限。

如果将来确实要做（例如换主体、或想让账号跨微信使用），必须**一次做对**，
因为它会改掉数据的归属主键：

1. 账单表加 `uid`，历史数据刷一遍（按 `_openid` 反查 `users` 补齐）
2. 所有 `where({ _openid })` 改成按 `uid` 过滤
3. **账单列表目前是客户端直查**，必须收口进云函数 ——
   云数据库的集合权限是围绕 `_openid` 判定的，uid 一旦跨 openid，客户端直查必然漏数据
4. 密码用 Node 内置 `crypto.scryptSync` 加盐哈希（`scrypt$N$r$p$salt$hash`），
   比对用 `timingSafeEqual`
5. **不需要自建 token**：手机号密码只在「登录那一次」校验，
   成功后把当前 openid 写进绑定关系，之后每次云函数直接用
   `cloud.getWXContext().OPENID` 反查 uid 即可，省掉一整套 session 与鉴权中间件

### 颜色硬编码红线

主题化之后，**页面 WXSS 里不允许再出现品牌色的十六进制字面量**。
需要品牌色一律用 `var(--brand*)`，需要固定色（如语义红绿、无彩色）才允许写死。
`tests/static-check.js` 会扫描 `--primary-color` 等已删除的旧变量名，写错会直接报错。

## 微信支付怎么接（会员真实收款）

> 现状：个人主体小程序**申请不了微信支付商户号**，所以会员入口已临时隐藏、
> 智能分析对所有人开放（`INSIGHT_REQUIRE_VIP=false`）。这一节是等主体换成
> 企业/个体工商户后，把真实收款打通的操作指南。代码里的接线位已经全部留好。

### 一、前置条件（顺序不能乱）

| 步骤 | 在哪操作 |
|------|---------|
| 1. 小程序开通微信支付 | 主体为企业/个体工商户，在公众平台申请商户号（需营业执照+对公账户） |
| 2. 关联 AppID | 微信支付商户平台 → 产品中心 → AppID 账号管理，绑定本小程序 |
| 3. 绑定商户号到云环境 | 云开发控制台 → 设置 → 全局设置 → 微信支付 → 填入 mchid |
| 4. 授权服务商 | 微信「支付商家助手」小程序 → 服务商授权 → 找到 `1800008281 小程序云开发` → 确认 |
| 5. 开产品权限 | 商户平台 → 我的授权产品 → 开启 **JSAPI 支付**（退款可选） |

缺任一步直接调 `cloudPay.unifiedOrder` 会报 `errCode: 47001`。

### 二、接入路径：云开发 `cloudPay`（不用自己签名）

本项目是云开发，**不要**自己搭服务器写签名 —— `cloud.cloudPay.unifiedOrder`
内部处理签名与证书，只需传业务参数。整个链路：

```
用户点「开通」→ 前端调 user 云函数(createVipOrder)
   ↓
云函数：生成 outTradeNo → 写 vip_orders 订单表 → cloud.cloudPay.unifiedOrder({...})
   ↓ 返回 payment（已签好名的支付参数）
前端：wx.requestPayment(payment) → 拉起微信收银台
   ↓ 用户付款
微信把结果推给 unifiedOrder 里指定的回调云函数（functionName: 'payCallback'）
   ↓ 云端验签（云调用自动做）→ 按 outTradeNo 找到 openid → 激活 VIP → 订单标记 paid
```

### 三、要改的四处（都在现有代码里留了位）

**1. `cloudfunctions/user/index.js` 的 `createVipOrder`** —— 删掉 sandbox 分支，换成真下单：

```js
async function createVipOrder(openid) {
  const got = await getProfile(openid)
  if (got.code !== 0) return got
  if (got.data.vip) return { code: 0, data: { alreadyVip: true, vip: got.data.vip } }

  const outTradeNo = 'VIP' + Date.now() + Math.random().toString(36).slice(2, 8).toUpperCase()
  await db.collection('vip_orders').add({ data: { outTradeNo, _openid: openid, status: 'paying', createdAt: Date.now() } })

  const res = await cloud.cloudPay.unifiedOrder({
    body: VIP_PRODUCT_NAME,        // 商品描述，会显示在收银台
    outTradeNo,                    // 商户订单号，回调靠它找人
    spbillCreateIp: '127.0.0.1',   // 用户 IP，云函数里拿不到真实值，占位即可
    subMchId: '<商户号>',          // 绑定的 mchid
    totalFee: VIP_PRICE_FEN,       // ⚠️ 单位是「分」，1800 = ¥18.00
    envId: 'cloud1-d7gne5bpf2229f19b',
    functionName: 'payCallback',   // ⚠️ 支付结果推给这个云函数，名字必须一字不差
    tradeType: 'JSAPI',
    openid
  })
  return { code: 0, data: { mode: 'wxpay', payment: res.payment } }
}
```

**2. 新增回调云函数 `cloudfunctions/payCallback/index.js`** —— 这是防白嫖的真正闸门：

```js
const cloud = require('wx-server-sdk')
cloud.init({ env: cloud.DYNAMIC_CURRENT_ENV })
const db = cloud.database()

exports.main = async (event) => {
  // cloudPay 回调已自带验签，进来的就是可信的支付结果
  const { outTradeNo, returnCode } = event
  if (returnCode !== 'SUCCESS') return { errcode: 0, errmsg: '处理失败' }

  const res = await db.collection('vip_orders').where({ outTradeNo }).limit(1).get()
  const order = res.data && res.data[0]
  if (!order) return { errcode: 0, errmsg: '订单不存在' }
  if (order.status === 'paid') return { errcode: 0 }   // 重复通知：幂等

  await db.collection('users').where({ _openid: order._openid })
    .update({ data: { vip: { since: Date.now() }, updatedAt: Date.now() } })
  await db.collection('vip_orders').where({ outTradeNo })
    .update({ data: { status: 'paid', paidAt: Date.now() } })
  return { errcode: 0 }
}
```

**3. `activateVip` 保持不动** —— `VIP_PAY_MODE !== 'sandbox'` 时它已经拒绝客户端直调，
真实激活只发生在回调里。它已有的幂等（已是会员就原样返回）正好防重复通知。

**4. 前端 `pages/vip/vip.js`** —— 收到 `payment` 后 `wx.requestPayment`，
`success` 里重新 `user.load()` 刷新会员态，而不是直接调 `activateVip`。

### 四、一定会踩的坑

| 坑 | 说明 |
|----|------|
| **金额单位** | `totalFee` 是**分**。前端展示用元，传给支付必须 ×100。传 18 会报"金额无效" |
| **订单必须落库** | 回调只给 `outTradeNo`，不落库就不知道该给谁开通 |
| **回调函数要单独部署** | `payCallback` 是独立云函数，改完 `user` 不会带上它 |
| **vip_orders 集合要建** | 云函数不会自动建集合（同 `users`，控制台手动建） |
| **集合权限** | `vip_orders` 设「仅创建者可读写」；`users` 仍是「仅管理端可读写」（云函数绕过权限写） |
| **body 中文乱码** | 不要自己编码，SDK 会处理 |
| **支付成功但界面没变** | `wx.requestPayment` 的 `success` 里必须重新拉一次档案，只弹 toast 会像没付上 |

## 注意事项

1. **隐私安全**：数据存在你自己的云环境里，查询一律带 `_openid` 隔离，仅本人可访问
2. **无需登录**：本项目**没有登录页，也不收集密码**。`wx.getUserProfile` 自 2021 年起已不再返回
   昵称头像，而所有查询都以云开发隐式提供的 `_openid` 为准，所以拿到身份不需要用户点任何授权。
   用户能设置的只有「昵称」这种展示用信息 —— 它不是账号，不能用来登录。
   详见「登录与用户体系」
3. **免费额度**：云开发免费额度足够个人使用（2GB 数据库 + 5GB 存储）
4. **账单格式**：目前按微信钱包导出的标准格式解析，其他平台格式需要补字段映射
5. **金额显示**：金额 ≥ 10 万才缩写成「万」，避免日常金额被显示成「1.44万」造成误解
6. **配色约定**：收入用红色、支出用绿色（沿用 A 股涨红跌绿的视觉习惯）。
   注意这组语义色**不随主题变化**——它是金融含义，不是品牌表达
7. **主题色**：默认微信绿，可在「我的 → 设置 → 主题颜色」里换。按钮/选中态/浅色底、
   首页 / 我的 / AI 分析的**顶部深色卡片**，以及**原生导航栏、下拉露出的底色**都会跟着变
   （导航栏与 tabBar 无法用 CSS 染色，只能由 JS 设置，所以色值在 `utils/theme.js` 里也有一份）。
   偏好同时存在于本机（`app_theme_id`，负责首帧与断网降级）和云端（`users.theme`，权威值），
   所以换手机 / 重装后会恢复你选的那套色
8. **收/支语义红绿不跟主题走**：它是金融含义。5 套 hero 都是深色，卡片上那组
   `--on-hero-income / --on-hero-expense` 也就只需一份（都在 `page` 上声明）

### 已知的取舍

- **编辑与删除都支持了**：改一笔从详情弹层的「编辑」进入（详情见上），
  删一笔有左滑与弹层两个入口。
  改一笔目前是「整条替换」而不是「只提交改动的字段」—— 云端按提交内容整体更新，
  这也是为什么编辑前必须把原值完整拉回来
- 新增一套主题要改四处（`utils/theme.js` 的 `THEMES` / `app.wxss` 的 `.theme-*`（13 个令牌）
  / 重新生成 tabBar 图标 / `pages/index/index.json` 的静态兜底色），
  这是「原生导航栏与 tabBar 都只能预生成或由 JS 设置」的必然代价；
  好处是主题切换零运行时开销（只是换个 class），且漏改任何一处静态检查都会报错
- **账号只有一层：openid。** 同一台手机换一个微信登录，看到的是另一个账本；
  反过来，同一个人换手机（仍是同一个微信）不受影响，数据照旧。
  这是「不做手机号 + 密码」的直接代价，换来的是零成本、无密码泄露风险、零登录摩擦。
  真要跨微信同步，就得按「登录与用户体系」末尾那 5 步做一次数据迁移
- **昵称可重名、不唯一。** 它只是显示名，不承担账号标识的职责，
  所以没有唯一性校验、也不需要敏感词库（真正的身份是 openid，改昵称换不来任何权限）
- 首页三个快捷入口的图标底色**不跟主题走**：那 3 个图标是固定色的 PNG，
  底色跟主题走会出现「蓝色图标配浅绿底」的割裂感。要它们也跟主题变，
  得先按主题再生成一套图标
- 分类是**关键词匹配**，不是模型推理：商户名里没有规则词时会落到「其他支出/其他收入」，
  这属于预期行为而不是 bug。要提升命中率就往 `smartClassify` 的规则表里加词
- 账单**时间统一按北京时间（UTC+8）**理解与显示。微信账单本身只有北京时间，
  没有时区字段，所以这里不做多时区支持
